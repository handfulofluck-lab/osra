## 4. Verification notes (why you can trust this report)

Findings are cheap; verified findings are not. Every critical/high claim was re-tested, and the
process changed several conclusions:

- **Verified, then upgraded to P0.** API-02 (`internalSecret` in `/me`, `/export`, `/devices`,
  `/devices/:id`, plus a device JWT reading a sibling's key) and API-01 (a device signing an alert
  into a *sibling* child — alert landed on the sibling's feed) and API-04 (after unpair: `/v1/rules`
  200, WS ticket 200, `/v1/location/ping` **500 leaking Prisma internals**).
- **Verified server-side.** IOS-01: an alert signed with the device's own secret but without a body
  `deviceId` → **401**; with `deviceId` → 201. The iOS reporter sends no `deviceId`, so every iOS
  alert would be dropped. Fixing this server-side also unblocks already-written iOS code that cannot
  be rebuilt here (no Mac).
- **Verified in source.** API-07: the live 15-minute password-reset JWT is written to the server log
  (`auth.ts:187`). API-03: nothing in the codebase reads `ConsentRecord.revokedAt`/`expiresAt`, and
  no revoke endpoint exists (404).
- **Refuted.** API-06 (concurrent refresh double-spend): a real parallel race returned `200,401` —
  not reproduced. Left in the report as a hardening note, not a bug, so nobody wastes time on it.
- **Corrected my own probe.** Two of my first-run failures (`F2`, `F4`) were my error — the refresh
  route is `/v1/auth/token/refresh`. Fixed before reporting; the corrected run gives the real picture.
- **Environment flake, not a bug.** The one API test failure is a 20 s timeout while gradle, flutter
  and five audits ran concurrently; it is an assertion-free timeout.

## 5. What could not be verified here

- **iOS/macOS do not compile on this host** (no macOS/Xcode). IOS-03/IOS-04 are compiler errors found
  by code reading; everything iOS needs a Mac to confirm end-to-end.
- **No physical Android device**: GPS/location and some accessibility behaviours remain unverified
  on real hardware (emulator GPS injection does not reach the agent).
- **Play Store / App Store readiness** is tracked separately in `docs/test-guides/PUBLISHING-READINESS.md`.
- **AI-engine quality** was only smoke-tested (18 tests); no adversarial NLP evaluation was run.

## 6. Priority order

1. **P0-1** secrets leak (API-02) — the key that proves alerts are genuine is handed out.
2. **P0-2** iOS alerts 401 (IOS-01) — an entire platform's safety pipeline is dead.
3. **P0-3** four alert categories rejected (AND-01) — tamper/VPN/install/unknown-contact are inert.
4. **P0-4** cross-child injection (API-01) — one child device can write another's safety history.
5. **P0-5** revocation scope (API-04) — unpaired devices keep working.
6. **P1** enforcement escape hatches (AND-02…05, WIN-01…06) and parent-app contract bugs (FLT-01…06).
7. **P2/P3**, then the three design targets (replay protection, consent revocation, command-queue drain).

## 8. Physical-device pass — 2026-10-11 (added after the merge of PR #15)

Run on the human's Samsung SM-F721B (Android 16) with the built APKs from `dist/`, the agent pointed at
the API through `adb reverse tcp:3000`.

**What works on real hardware**

- Install + launch of both APKs; the parent app's server field is blank on first run (re-confirmed on
  hardware, not just the emulator).
- Pairing: `POST /v1/devices/pair/claim → 201`, followed by `GET /v1/rules/<childId> → 200`.

**New findings (both critical, neither was visible on the emulator or in any suite)**

| ID | Finding | Evidence |
|---|---|---|
| AND-13 | The agent **crash-loops**: `startAgent()` starts the location FGS before any location permission exists → `SecurityException` at `LocationService.kt:201` (from `onStartCommand:92`); the sticky service is restarted and crashes again — **7 FATAL exceptions**, live PID, no FGS | logcat trace, captured verbatim in `ANTIGRAVITY-INBOX.md` P0-6 |
| BUG-001 | Android **location uploads can never succeed**: the agent posts `{pings:[{lat,lng,accuracyM,timestamp}]}` (no `childId`/`deviceId`) while the API expects a flat identified object; live attempts all failed — **7 of 7 completed requests were HTTP 500**, `Foreign key constraint violated` (stale `deviceId` replayed by the pending-ping worker) | `LocationService.kt:184`, `PendingPingWorker.kt:35`, `routes/location.ts` + API log |

**Correction to §1 of this report — my error.** I wrote that the emulator's missing location was due to
GPS injection not reaching the agent. The device pass shows the deeper cause: Android location uploads
cannot succeed at all (envelope + missing identity + FK on replay), independent of GPS. GPS injection
may still be an emulator limitation, but it was **not** the root cause and my earlier attribution was
incomplete. The emulator result should have been reported as "unverified", not "blocked by injection".
