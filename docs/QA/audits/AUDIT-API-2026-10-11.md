## API audit

Findings are ranked by impact. All paths/line numbers verified against the actual files in `services/api`.

---

- **ID**: API-01
- **Severity**: high
- **File**: `services/api/src/lib/internalAuth.ts:20-35`, `services/api/src/routes/alerts.ts:87-101`, `services/api/src/routes/location.ts:45-55,110-120`, `services/api/src/routes/social.ts:90-99`
- **What breaks**: The per-device HMAC path authenticates the *device* but never binds the body `childId` to the signing device's family. `verifyInternalSignature` returns only a boolean and looks up the secret by the client-supplied `deviceId`; the routes then trust the body `childId` verbatim. `/v1/alerts/internal`, the HMAC fallback of `/v1/location/ping`, and `/v1/social/scan` all do `child.findUnique({where:{id:childId}})` with **no** check that `child.familyId` matches the device's family.
- **Repro**: A device (which holds its own `internalSecret`, returned at pair/claim in `devices.ts:158`) signs a body with `deviceId = <own>` and `childId = <any sibling childId>` (sibling IDs are learnable via `GET /v1/devices`, see API-02). The signature verifies against the device's own secret, and the alert/ping/SocialEvent is written against the sibling. The JWT path of `/ping` *does* check `child.familyId !== user.familyId` (`location.ts:113`), but the HMAC path has `req.user` undefined so the check is skipped — proving the family check is absent for HMAC callers.
- **Expected vs actual**: Family isolation should reject any HMAC request whose `childId` is outside the signing device's family. Actual: accepted, and geofence/alerts/push events are fired into the wrong child's family (`publishFamilyEvent(child.familyId, …)`).
- **Suggested fix direction**: In `verifyInternalSignature`, return the device's `childId`/`familyId` (not just `boolean`) and have each route assert `device.child.familyId === child.familyId` (and `device.childId === childId`). At minimum, resolve the device first and reject on family mismatch.

- **ID**: API-02
- **Severity**: high
- **File**: `services/api/src/routes/devices.ts:163-171` (list) and `176-179` (get one); schema at `prisma/schema.prisma:60,62`
- **What breaks**: `GET /v1/devices` uses role-agnostic `requireAuth`, and `GET /v1/devices/:id` uses role-agnostic `requireFamily({model:"device"})` (which only checks family, not child). Both return the full Prisma `Device` row — including `internalSecret` (the per-device HMAC secret) and `pushToken` — with no field stripping. A device JWT (`role:"device"`, carries `familyId`/`childId`) can enumerate every device in its family and read every sibling's `internalSecret` + `pushToken`.
- **Repro**: Sign a device JWT (`deviceHeader` in `test/helpers.ts:104-110`), then `GET /v1/devices` → response contains sibling devices' `internalSecret`. Those secrets can then be used to sign `/v1/alerts/internal`, `/v1/social/scan`, `/v1/location/ping` *as* those devices (making API-01 fully practical within the family).
- **Expected vs actual**: Per-device HMAC secrets must never leave the server; the recently-fixed push-token strip only covered `/family/me` and `/export` — the `/devices` routes were missed. Actual: secrets returned to device JWTs.
- **Suggested fix direction**: Add a `select` that excludes `internalSecret`/`pushToken` on the list and single-device GET, or gate both behind `requireParent`; also scope `requireFamily({model:"device"})` so a device may only read its *own* row (`device.childId === user.childId`).

- **ID**: API-03
- **Severity**: high
- **File**: `services/api/src/routes/family.ts:63-107` (only gate), `family.ts:117-123`, `rules.ts:145-160,163-201`, `controls.ts:40-117`, `location.ts:169-175`, `devices.ts:93-104,107-117`
- **What breaks**: The consent gate (invariant b) is enforced **only** at child creation (`POST /v1/family/children`). Every other child-scoped write — `PATCH /children/:id`, `PUT/PATCH /rules/:childId`, `pause/resume/bonus/wind-down`, `POST /location/geofences`, `POST /devices/register`, `POST /devices/pair` — writes child-scoped data with no check for a live `ConsentRecord`. There is also **no endpoint that revokes consent** and **no code path that ever reads `ConsentRecord.expiresAt` or `revokedAt`**; both columns are dead for enforcement.
- **Repro**: Create a child with inline consent, then delete/expire that consent (or set `revokedAt` in the DB). All subsequent rules/controls/geofence/device writes still succeed (200/201) — the 428 gate never runs.
- **Expected vs actual**: "child-scoped writes require a live ConsentRecord → 428". Actual: only child creation is gated; revocation/expiry are never enforced anywhere.
- **Suggested fix direction**: Add a shared `requireConsent(childId)` preHandler (checks a non-expired, non-revoked, jurisdiction-matching `ConsentRecord`, else 428) and apply it to the write routes above; add a `POST /children/:id/consent/revoke` (or `revokedAt` setter) endpoint.

- **ID**: API-04
- **Severity**: high
- **File**: `services/api/src/routes/devices.ts:287-297` (scoped hook), `routes/rules.ts:138`, `routes/location.ts:45-55,132,143`
- **What breaks**: The revoked-device check is registered via `app.addHook("preHandler", …)` **inside** `deviceRoutes`, which is mounted with `prefix:"/v1/devices"` (`server.ts:55`). Fastify encapsulation means the hook only runs for `/v1/devices/*`. A revoked (unpaired) device's 10-year JWT still passes `req.jwtVerify()` on every other role-agnostic route.
- **Repro**: Unpair a device (`DELETE /v1/devices/:id` writes `revoked:device:<id>`). The device can still `GET /v1/rules/:childId` (`rules.ts:138`), `GET /v1/location/:childId/latest` and `/history` (`location.ts:132,143`), and — most importantly — `POST /v1/location/ping` (`location.ts:105`, `pingAuth` only calls `req.jwtVerify()`), so a revoked device keeps reporting location and triggering geofence alerts indefinitely. The test `token-hygiene.test.ts:126-138` only exercises `GET /v1/devices/:id`, so the gap is untested.
- **Expected vs actual**: "revoked devices must fail" everywhere. Actual: only `/v1/devices/*` is guarded.
- **Suggested fix direction**: Register the revocation hook on the root `app` (in `server.ts` or a shared plugin) so it runs for every route, not inside the devices plugin.

- **ID**: API-05
- **Severity**: medium
- **File**: `services/api/src/routes/invites.ts:85-89`, `routes/auth.ts:118,137`
- **What breaks**: Accepting an invite (`POST /v1/family/invites/:id/accept`) updates `parent.familyId` to the new family but does **not** revoke that parent's existing access token or refresh tokens. Parent access tokens are stateless JWTs valid for 7 days carrying the *old* `familyId`, so after a family transfer the parent retains read/write access to the previous family for up to 7 days. (Refresh tokens are partially mitigated because refresh re-derives `familyId` from the DB at `auth.ts:242`, but the access token itself is unaffected.)
- **Repro**: Parent P in family A accepts an invite to family B. P's still-valid access token (issued for A) continues to satisfy `requireFamily` for A's resources until the 7-day expiry.
- **Expected vs actual**: A parent may only read/write their *current* family. Actual: prior-family access persists for the token TTL.
- **Suggested fix direction**: On invite accept, call `revokeAllRefreshTokens(parent.id)` and add access-token revocation (e.g. a `tokenVersion`/`iat` claim checked against a stored value, or a deny-list).

- **ID**: API-06
- **Severity**: medium
- **File**: `services/api/src/routes/auth.ts:221-245`
- **What breaks**: Refresh-token rotation is not atomic. Two concurrent `POST /token/refresh` calls with the same token both run `get(liveKey)` (`:221`) before either executes `del(liveKey)` (`:238`), so both read the stored value, both pass the expiry check, and both rotate — each mints a fresh token/session. Reuse detection (`usedKey`) only catches a *sequential* replay after the first rotation completes.
- **Repro**: `Promise.all([refresh(rt), refresh(rt)])` — both return 200 and two new sessions are issued from one refresh token.
- **Expected vs actual**: A refresh token must be consumable exactly once. Actual: concurrent double-spend.
- **Suggested fix direction**: Consume the token atomically (Lua `GET`+`DEL`, or `GETDEL`, or `SET usedKey NX` as the gate) before issuing new credentials — the same pattern already used for pairing codes at `devices.ts:126-130`.

- **ID**: API-07
- **Severity**: medium
- **File**: `services/api/src/routes/auth.ts:181-189`
- **What breaks**: `POST /auth/reset/request` prints the live 15-minute password-reset JWT to the server log: `console.log('[email:stub] password reset for …: ${token}')`. This is a bearer credential that resets the account password (`reset/confirm` trusts it at `auth.ts:202`). It violates invariant (h) "no secrets in logs" and, because there is no env guard, it will still run in production even though email delivery is stubbed.
- **Repro**: Trigger a reset; anyone with log access can replay the token and take over the account.
- **Expected vs actual**: Reset token should be delivered out-of-band, never logged. Actual: token in plaintext in logs.
- **Suggested fix direction**: Remove the token from the log line (log only the email stub), and gate the whole stub behind a non-production check.

- **ID**: API-08
- **Severity**: low
- **File**: `services/api/src/routes/auth.ts:43-47`
- **What breaks**: The TOTP replay guard reads `mfa:lastcounter:<parentId>` and then `SET`s it non-atomically. Two concurrent logins presenting the same code can both observe `last === null` before either write, so the same TOTP code can be used twice within one 30s window (TOCTOU).
- **Repro**: Race two `POST /login` requests with the same `code`; both can pass.
- **Expected vs actual**: A captured TOTP code must be single-use. Actual: replay possible under concurrency.
- **Suggested fix direction**: Use an atomic guard such as `SET key counter NX` (or a Lua compare-and-set) and treat "already set to ≥ counter" as a failure.

- **ID**: API-09
- **Severity**: low
- **File**: `services/api/src/realtime/gateway.ts:37-40`
- **What breaks**: WS ticket single-use is enforced with a non-atomic `get` then `del`. Two concurrent WS connections presenting the same ticket both read the familyId before either deletes, so both connect (the pairing-code path uses atomic Lua, but tickets do not).
- **Repro**: Open two `GET /v1/ws?ticket=<t>` connections simultaneously; both authenticate.
- **Expected vs actual**: Tickets must be single-use. Actual: raceable.
- **Suggested fix direction**: Consume atomically (`EVAL` GET+DEL) and reject when the returned value is null.

- **ID**: API-10
- **Severity**: medium
- **File**: `services/api/src/routes/rules.ts:16-28`, `routes/controls.ts:10-16`, `prisma/schema.prisma:71-72`
- **What breaks**: `ScreenTimeSchema.dailyLimitMinutes`/`weekendLimitMinutes` and `BonusSchema.minutes` are `z.number().int().min(0)` (or `.min(1)`) with **no upper bound**, but the corresponding Prisma columns are 32-bit `Int`. A value like `2147483648` passes validation and then Prisma throws an out-of-range error; there is no `setErrorHandler` in `server.ts`, so the raw Prisma error is serialized to the client (500) and may leak SQL/internals.
- **Repro**: `PUT /v1/rules/:childId` with `dailyLimitMinutes: 99999999999` → 500 with Prisma error details.
- **Expected vs actual**: Inputs should be rejected with 400 before hitting the DB. Actual: unhandled DB error surfaces.
- **Suggested fix direction**: Add `.max(2147483647)` (or a sane product bound) to every `Int`-backed field, and add a global error handler that maps Prisma errors to a generic 400/500 without internals.

- **ID**: API-11
- **Severity**: low
- **File**: `services/api/src/lib/snippetVault.ts:7-10`
- **What breaks**: When `VAULT_KEY` is unset, the vault derives its AES key deterministically from `JWT_SECRET`: `sha256(JWT_SECRET).digest("base64")`. In dev/test, `JWT_SECRET` is a known value (`dev-secret-change-me` / `e2e-dev-secret`, per `server.ts:24`), so "encrypted-at-rest" social-message snippets are decryptable by anyone who knows the dev secret. Production is guarded by the `VAULT_KEY` check in `server.ts:30-32`, but the fallback itself is not gated.
- **Repro**: With a dev JWT_SECRET, compute the fallback key and `decryptForFamily` any `SocialEvent.previewCipher`.
- **Expected vs actual**: Vault must be encrypted with a real key. Actual: deterministic key from a known secret in non-prod.
- **Suggested fix direction**: Derive the fallback from a dedicated non-secret-independent source or refuse to start (throw) when `VAULT_KEY` is missing outside an explicit test flag, mirroring the JWT_SECRET guard.

- **ID**: API-12
- **Severity**: low
- **File**: `services/api/src/realtime/gateway.ts:17-26`
- **What breaks**: `POST /v1/ws-ticket` is role-agnostic (`req.jwtVerify()` only). A device JWT can mint a WS ticket and subscribe to `family:<familyId>:events`, receiving the family's realtime stream — including social-concern alerts (which carry `app`/`contact`/`concernTypes` metadata, `social.ts:124-135`) for all children in the family, not just the device's own child.
- **Repro**: Device JWT → `POST /v1/ws-ticket` → connect `GET /v1/ws?ticket=…` → observe sibling alerts.
- **Expected vs actual**: Parent-facing realtime events should be parent-only. Actual: any device in the family can subscribe.
- **Suggested fix direction**: Require `role === "parent"` on `/v1/ws-ticket` (or split device vs parent channels).

### Verified solid

- **Parent-only mutations are consistently gated**: every parent write composes `requireParent`, which rejects non-`parent` roles with 403 — device JWTs cannot reach parent-only routes (`requireFamily.ts:42-52`, e.g. `devices.ts:183,206,277`, `rules.ts:145,163`, `controls.ts:42-111`, `location.ts:169,178`).
- **`requireFamily` scoping holds for JWT-authenticated routes**: child/device/geofence/alert IDs are resolved through their `child.familyId` and cross-family access returns 403 (`requireFamily.ts:59-91`).
- **Sequential refresh-token replay is detected and revokes the family's sessions** via `refresh:used` + `refresh:owner` (`auth.ts:222-231`; covered by `token-hygiene.test.ts:65-81`).
- **HMAC comparison is constant-time** (`timingSafeEqual` with a length pre-check) and fails closed when `INTERNAL_HMAC_SECRET` is unset (`internalAuth.ts:31-35`).
- **Pairing-code claim is atomic and single-use** (Lua GET+DEL), and each device gets its own per-device secret at claim time rather than the global HMAC secret (`devices.ts:120-138`; `token-hygiene.test.ts:150-172`).
- **Push tokens and parent credentials are stripped** from `/family/me` and `/export`, and parent rows are sanitized (`passwordHash`/`mfaSecret` removed) (`family.ts:32,50-56,183-189`).

Note: API-01's cross-family exploit requires knowing a foreign child UUID (not enumerable via these endpoints), so the fully practical impact today is within-family cross-child injection; the invariant is nonetheless not enforced in code. API-06/08/09 are race conditions not reproducible in the single-threaded mock-Redis tests, which is why they're green but still present.
