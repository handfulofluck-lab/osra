# Localization (English and Arabic)

The parent app ships English and Arabic UI. Arabic is a right-to-left (RTL) language, so a
translation is not finished until the same screen also lays out correctly in RTL.

**Arabic wording has one owner: the Arabic Language Bureau** (maintainer, 2026-11-12; `AGENTS.md` §13).
Before you write or change an Arabic line anywhere (apps, website, store listing, guide, email, push,
video), read [the Bureau's rules and word list](#arabic-language-bureau-plan-321) at the end of this
file, then ask for a review on issue #604.

## Layout

| Path | What it is |
|---|---|
| `apps/parent-app/l10n.yaml` | Generation config: ARB directory, English template, output class `AppLocalizations` |
| `apps/parent-app/lib/l10n/app_en.arb` | English template — the source of truth for keys and placeholders |
| `apps/parent-app/lib/l10n/app_ar.arb` | Arabic translations, one entry per English key |
| `apps/parent-app/lib/l10n/app_localizations*.dart` | Generated by `flutter gen-l10n`; do not edit by hand |
| `apps/parent-app/lib/l10n/l10n.dart` | `context.l10n`, `context.localeName`, and label maps for API values (categories, severities, command states) |
| `apps/parent-app/lib/providers/locale_provider.dart` | Persisted override (`app_locale`: `system` / `en` / `ar`) |

`MaterialApp` in `lib/app.dart` receives `localizationsDelegates` and `supportedLocales` from
`AppLocalizations`, and `locale` from `localeProvider`. A `null` locale follows the device;
Settings → Appearance can pin English or Arabic. The choice is written to
`shared_preferences` under `app_locale`, the same way `theme_mode` is persisted.

## Add a string

1. Add the key and English copy to `lib/l10n/app_en.arb`. Give every placeholder a type:

   ```json
   "screenTimeValue": "{minutes} / {limit} min",
   "@screenTimeValue": {
     "placeholders": {
       "minutes": { "type": "int" },
       "limit": { "type": "String" }
     }
   }
   ```

2. Add the same key to `lib/l10n/app_ar.arb` with real Arabic (not a transliteration), and use
   ICU plural categories where Arabic differs — `zero`, `one`, `two`, `few`, `many`, `other`:

   ```json
   "callsCount": "{count, plural, =0{لا مكالمات} =1{مكالمة واحدة} =2{مكالمتان} few{{count} مكالمات} many{{count} مكالمة} other{{count} مكالمة}}"
   ```

3. Run `flutter gen-l10n` (or `flutter pub get`). The generated files are checked in.
4. Use `context.l10n.yourKey` in the widget. For dates use
   `DateFormat.yMMMd(context.localeName)`, not the process default.
5. Run `flutter test test/localization_test.dart`. It fails if the Arabic key is missing,
   empty, has different placeholders, if a category in the server's `InternalAlertSchema` has no
   title in either locale, or if any translated screen overflows at 320×568 in RTL.

Do not add a user-visible literal to a screen. Values that arrive from the API (app names, child
names) stay as the server sent them; enum-like values (web-filter categories, alert categories and
titles, search risk tags, command types, severities) are mapped through `l10n.dart` so the raw value
is never shown when a translation exists. The one deliberate exception is an alert category the app
does not know yet: English shows the server's own title, any other locale shows the translated
generic, so server English never reaches an Arabic screen.

## Add a language

1. Copy `app_en.arb` to `app_<code>.arb`, set `@@locale`, and translate every value. Keep the
   key set identical; `flutter test test/localization_test.dart` enforces that for Arabic today
   (add the new file to that test's parity check when a third language lands).
2. Add the language to `supportedLocales` automatically — it is generated from the ARB files.
3. Add the display name and a provider choice:
   - `lib/providers/locale_provider.dart`: map the code in `appLocaleFromName`.
   - `lib/features/settings/appearance_screen.dart`: add a dropdown item and its two status
     strings.
4. Add one Arabic-style widget test per screen for the new language: locale, explicit
   `Directionality`, 320×568, no overflow.
5. If the language is RTL, it needs no code change beyond step 1 — the layout rules below are
   direction-agnostic.

## Android child agent

The child agent does not use ARB. Its strings are Android resources: `res/values/strings.xml` is
English and `res/values-ar/strings.xml` carries Arabic (today the ADR-0031 reset-code notice; keys not
translated there fall back to English). That notice is centred, so it reads correctly in RTL without a
manifest-wide `android:supportsRtl` change — with one exception that must stay: **the reset code is
set `TextDirection.Ltr`**, because `1234 5678` has no strong character and an RTL paragraph would
render it `5678 1234`. Add new user-visible copy to both files. **Counted copy is a `<plurals>`
resource in both files, read with `pluralStringResource`**: Arabic needs all six CLDR quantities
(`one`, `two`, `few` for 3–10, `many`, `other`, `zero`), so a plain `%1$d دقيقة` is ungrammatical for
most of a code's life. `ResetCodeStringsTest` compares the EN and AR key sets across strings and
plurals alike.

## RTL rules for screens

- Use `EdgeInsetsDirectional` / `AlignmentDirectional` and `start`/`end`; never
  `EdgeInsets.only(left:)`, `EdgeInsets.fromLTRB`, or `Alignment.centerLeft` for chrome.
- Do not hard-code `TextDirection`. `MaterialApp` derives it from the locale; tests wrap a
  screen in `Directionality(textDirection: TextDirection.rtl)` to prove it.
- `Row`, `Wrap`, `TabBar` and `AppBar` actions mirror automatically. Prefer `Wrap` over a
  fixed `Row` where translated labels are longer, and make tab bars scrollable when four or
  more labels must fit 320 px.
- Directional icons (`Icons.chevron_left/right`, `arrow_*`) mirror from their
  `matchTextDirection` flag; check any icon that does not.
- `apps/parent-app/android/app/src/main/AndroidManifest.xml` sets `android:supportsRtl="true"`
  for native widgets and the app-switcher label.

## Arabic Language Bureau (plan 3.21)

The maintainer set this up on 2026-11-12 after scoring a draft Arabic page "75% in 20% of the document
and 95% in the rest". His words (capitals lowered, words unchanged): *"maybe that should be a best
practice across the team, we make a thread for Arabic word checking … like our Arabic Language Bureau
and we can add more languages and bureaus in the future"*, and a minute later: *"yes it handle all
Arabic communication, content...etc"*.

The Bureau is Claude, working in its own lane. It is the single reviewer for every Arabic word a parent,
a child or a store reviewer will read.

**Who decides (maintainer, 2026-11-13).** Until 12 November the maintainer approved every line himself.
On 13 November he changed that, in his words: *"The bureau should take the decision after its internal
thorough process to decide based on comparison and standards."* So the Bureau now decides the wording
and reports to him what it decided. Three things stay as they were: a row in "Karim's corrections" binds
the Bureau like everyone else; any wording he gives later overrides the Bureau's and becomes such a row;
and he is told of every decision, so he can still change it.

### What goes through the Bureau

| Surface | Where it lives |
|---|---|
| Parent app | `apps/parent-app/lib/l10n/app_ar.arb`, `apps/parent-app/ios/Runner/ar.lproj/`, `lib/features/coach/coach_content.dart` |
| Child apps | `apps/child-android/app/src/main/res/values-ar/`, `apps/child-ios/**/ar.lproj/` |
| Website | `site/**` (Arabic pages, drawings, video captions) |
| Store listings | `docs/store/**` |
| Customer guides | `docs/customer/**` |
| Emails and push | `services/api/src/lib/email/templates.ts`, the Arabic in `services/api/src/routes/account.ts` and `digests.ts` |
| Anything sent to people in Arabic | support replies, announcements, release notes |

Out of scope: test fixtures, and the AI evaluation banks under `services/ai-engine/eval/`, which imitate
children's messages in dialect on purpose.

### How a line gets approved

1. **Draft.** The author writes the Arabic in the PR and lists the changed lines in a table in the PR
   body: where the line shows, the English, the Arabic.
2. **Ask.** Comment `Bureau review: #<PR>` on issue #604, with who reads the text (parent, child, store
   reviewer).
3. **Bureau review.** The Bureau answers on the PR line by line: OK, or the wording to use and the rule
   it comes from. When every line is settled it signs `Arabic-Bureau: reviewed <head sha>` on the PR.
4. **The Bureau decides** (since 2026-11-13; before that the maintainer answered a numbered sheet or a
   card). A decision is made only after the four checks below, and the comment that gives it names what
   it rests on.
5. **Record and report.** The decided wording goes in with a comment naming the decision (date, PR), and
   a test pins it where the suite allows (`ChildSystemStringsTest`, `localization_test.dart`). A new
   term goes in the word list marked **B** with its date. The Bureau tells the maintainer what it decided
   in plain words. A correction from him becomes a row in "Karim's corrections" below.

Nobody edits a decided or approved Arabic line without going round this loop again.

#### The four checks before the Bureau decides

1. **His corrections and the word list.** A row in "Karim's corrections" or a **K** term is used as it
   is. One thing has one name on every surface.
2. **Comparison.** Where the term exists there, the Bureau reads how the phone's own Arabic says it
   (Android, Samsung, Apple, Windows, from their resources or support pages, R8) and how the leading
   apps in the field say it ("How the leading apps say it"), and names the source.
3. **Standards.** The writing rules R1 to R12: grammar, one register, no gendered verb on a filled-in
   name, digits, direction, length for the place it shows.
4. **Where it shows.** The line is read in its screen or page (a screenshot or the built page), not only
   in the file.
   A screen that only a real phone can draw (the iPhone block screen, a system prompt) is the one
   exception: the Bureau signs on checks 1 to 3, says on the PR that the on-device read is owed, and
   reads the line on the device row before that build reaches anyone outside the team. A wrong fit found
   there is a follow-up line from the Bureau, never a silent edit.

**Honest limit.** When the Bureau also wrote the Arabic, checks 1 to 4 are a second reading by the same
agent, and since 13 November no person reads the line before it ships. That is the maintainer's choice;
it is stated here and on the PR, not hidden. Names of the apps, store text and headlines are still
reported to him one by one, because they are the hardest to change later.

### Why the weak 20% was weak

The first audit (2026-11-12) compared our Arabic with the Arabic that Google, Apple, Samsung and
Kaspersky publish for the same features, and with the maintainer's own corrections. Short labels were
already good. The weak part was almost always **long text**: explanations, install steps, marketing
paragraphs. Five habits caused it, and the rules below exist to stop them:

1. A sentence translated from English clause by clause, so it has no subject of its own
   («يطلب كل إذن على حدة ويشرح سبب الحاجة إليه»: who asks?).
2. The brand used as a bare noun. «أسرة» also means "a family", so «افتح أسرة» reads "open a family".
3. Two words for one thing, often inside one page (`تحميل` for both "download" and "reload").
4. A setting or button named differently from what the phone shows, so the parent cannot find it.
5. Clipped phrases where Arabic expects the full one («من يوم تفعيلها», «حتى وتطبيق المحادثة مغلق»).

### Writing rules

**R1. Write it in Arabic; do not translate it.** Read the Arabic with the English covered. Every
sentence names its subject, verbs come first where that is natural, and a long English sentence becomes
two Arabic ones. If a native reader would never say it that way, rewrite it.

**R2. Modern Standard Arabic, plain and warm.** The readers are families in the Gulf and the wider
Middle East. No dialect, no country-specific spelling («جوجل», «قوقل»), no English word in Arabic
letters where an Arabic word is established («ضروري», never «لازم»; «يستلم», never «يلتقط»).

**R3. Say the whole thing.** This is the maintainer's most frequent correction (2026-10-23):

- no abbreviations: «7 أيام», «30 يومًا», «يوميًا», never «7 ي» or «دقيقة/يوم»;
- name the thing: «تنتهي صلاحية الرمز», not «تنتهي الصلاحية»; «البريد الإلكتروني», not «البريد»;
  «وسائل التواصل الاجتماعي», not «التواصل الاجتماعي»;
- a label takes a colon before its value: «الإجمالي: 300 دقيقة».

**R4. Who we speak to.** A parent is addressed in the masculine singular, which Arabic reads as neutral
(«أدخل», «اضغط», «طفلك»). A child is addressed the same way, and their parent is always «والدك أو
والدتك». Parents as a group are «أولياء الأمور» or «الوالدان», never «الآباء» alone, which reads as
"fathers".

When the subject of a sentence is a name the app fills in (`{child}`, `{parent}`), the app does not know
whether it is a boy or a girl, a father or a mother. Do not hang a gendered verb on it: «طلب سماح من
{child}», not «{child} يطلب السماح»; «ردّ {parent}: ليس الآن», not «قال {parent}».

**R5. Buttons, steps, status.**

| Kind of text | Form | Examples |
|---|---|---|
| Button, menu item, tab | verbal noun, no full stop | «حفظ», «إلغاء», «متابعة», «تنزيل», «تسجيل الدخول» |
| Step or instruction | imperative, full stop | «افتح تطبيق أسرة على هاتف طفلك.» |
| Something that happened | «تم» + noun, or a passive verb | «تم الحظر 12 مرة», «تم بلوغ الحد اليومي», «أُرسل الطلب» |
| Something that failed | «تعذّر» + noun, then what to do | «تعذّر تحميل التنبيهات. حاول مرة أخرى.» |
| In progress | «جارٍ» + noun + … | «جارٍ الحفظ…» |
| Empty state | a full sentence | «لم يتم رصد أي عمليات بحث تستدعي الإبلاغ عنها» |

Some approved buttons are imperatives («ابدأ», «أقرن الآن», «اطلب السماح»). They stay until their
screen is next revised.

**R6. The brand.** In an Arabic sentence the product is «تطبيق أسرة», and it is grammatically masculine
(«يراقب تطبيق أسرة…», never «تطلب أسرة»). Write «تطبيق» before the name at least the first time in any
text, and every time the name would otherwise start the sentence or follow a verb. The family account is
«العائلة», never «الأسرة», so the brand and the common noun cannot be confused. The children's app is
«أسرة للأطفال». The maintainer decided on 2026-11-12 that this holds inside the apps too: the Latin
`OSRA` stays only in the logo. The 29 app lines that still carry `OSRA` move to «تطبيق أسرة» (backlog on
issue #604).

**R7. Other companies' names are written in Arabic letters where Arabic has one common spelling**
(maintainer, 2026-11-12, replacing the Bureau's earlier "always Latin"). In our own sentences write the
spelling in the table below. A name that is not in the table comes to the Bureau before it is used.

| Name | Write | |
|---|---|---|
| WhatsApp | «واتساب» | K 12 Nov |
| YouTube | «يوتيوب» | K 12 Nov |
| iPhone | «آيفون» | K 12 Nov |
| TikTok | «تيك توك» | B |
| Snapchat | «سناب شات» | B |
| Android | «أندرويد» | B |
| Chrome | «كروم» | B |
| Google | «جوجل» | K 12 Nov |
| Instagram | «إنستجرام» | K 12 Nov |
| Samsung | «سامسونج» | K 12 Nov |
| Google Play | «جوجل بلاي», usually «متجر جوجل بلاي» | B, from the row above |
| Apple | «آبل» | B |
| App Store | «آب ستور» | B |
| iPad | «آيباد» | B, from «آيفون» |
| Windows | «ويندوز» | B |
| Mac | «ماك» | B |
| Intel | «إنتل» | B (AMD and ARM are initials and stay Latin) |

The "g" sound in a foreign name is written «ج» (maintainer, 2026-11-12), never «غ» or «ق»: «جوجل», not
«غوغل» or «قوقل».

An Arabic-letter name takes no «ال» and joins its prefix like any Arabic word: «على يوتيوب», «وواتساب»,
«لآيفون». A Latin word that has to stay (a quoted label, a code) joins a one-letter prefix with a
tatweel and a space («لـ PIN»).

Three things are not covered by this rule and stay as they are:

- **A label quoted from the phone's screen** (R8). The reader has to find it, so it is written letter
  for letter as the phone draws it, inside «»: «Google Play للحماية».
- **A name filled in at run time**: an app's label read from the child's phone, a group's name, a
  person's name. It is shown as stored, inside FSI/PDI (R11).
- **Abbreviations that are not company names**: SMS, PIN, QR, an email address, a web address.
- **A store's own badge** («احصل عليه من Google Play», «تنزيل من App Store»): the badge is the store's
  artwork and wording, so the store's name stays in Latin letters inside it.

**R8. Name a setting the way the phone names it.** When a step tells the reader to tap something that
Android or iOS draws, quote the phone's own Arabic label inside «». Samsung and stock Android disagree
(see "What the phone shows"), so check the label on the test phone in Arabic before it ships, and when
a page serves both, give both: «افتح الإعدادات (أو الضبط في هواتف سامسونج)».

When the phone cannot be set to Arabic, read the label from the platform's own Arabic resources (for
iOS, the Simulator runtime's `ar.lproj` strings) or from the maker's Arabic support pages, and say
which source was used. When the phone's label has quote marks of its own, keep the words exactly and
drop the inner marks, because our «» already frame the label: iOS shows the button
`التغيير إلى "السماح دائمًا"` and we write «التغيير إلى السماح دائمًا».

Apple's Arabic labels, read from the iOS 27.2 Simulator runtime (CoreLocation, `locationd.strings`) and
Apple's Arabic support pages on 2026-11-12: «الإعدادات», «مدة استخدام الجهاز», «المشاركة العائلية»,
«حساب Apple», «السماح أثناء استخدام التطبيق», «السماح لمرة واحدة», «عدم السماح», «التغيير إلى السماح
دائمًا», «الإبقاء على أثناء الاستخدام», and the Settings row «دائمًا».

**R9. Numbers, dates, time.**

- Western digits everywhere (`0–9`), never «٠–٩», on every surface.
- A counted noun always goes through a plural rule with all six Arabic forms (ICU in ARB, `<plurals>`
  on Android): «دقيقة واحدة», «دقيقتان», «3 دقائق», «11 دقيقة». Where no plural mechanism exists (an
  email template, a web page), reword so that no noun follows the number («المدة بالدقائق: 45»).
- A duration that the system fills in comes in the nominative («ساعتان», «يومان»). Never put it after
  «منذ» or any word that needs the genitive; use the system's relative phrase («قبل ساعتين») or make the
  duration the subject. Check the dual (2) of every unit before a line with a filled-in time ships.
- System formatters follow the phone's region and print «٣» in Saudi Arabia and Egypt. Pin Latin digits
  in code (iOS: a locale with `numbers=latn`).
- Time is 24-hour `HH:MM`. Dates are Gregorian, day then month then year, with the month names «يناير،
  فبراير، …».
- The weekend differs by country: Friday and Saturday in Saudi Arabia, Qatar, Kuwait and Egypt, Saturday
  and Sunday in the UAE. Never name the days for "the weekend"; write «عطلة نهاية الأسبوع».

**R10. Punctuation and spelling.**

- Arabic marks: «،» «؛» «؟». Quotes are «…» only. One ellipsis character «…».
- Body sentences end with a full stop. Buttons, titles and labels do not.
- Tanween sits on the letter before the alif: «مجددًا», «فورًا», not «مجدداً».
- Hamza, «ة» and «ى» are always written correctly. A shadda or a short vowel is added only where the
  word could be misread: passive verbs («يُرسَل», «تُحفظ») and words like «مسجّل», «تحقّق».
- No tatweel for decoration and no letter-spacing on Arabic text.

**R11. Mixed direction.** A Latin word, a number with a unit, a code or a URL inside an Arabic sentence
is isolated: FSI/PDI around placeholders in the apps (the `BlockWindowCopy` pattern), `<bdi>` or
`dir="ltr"` in HTML, and a code such as `1234 5678` is forced left to right. Start a sentence with an
Arabic word, not a Latin one («رمز PIN…», not «PIN…»). Pages carry `lang="ar" dir="rtl"`.

**R12. Tone.** Calm and respectful, never frightening. We are honest that this is monitoring: any
sentence that says what is collected, and every consent or privacy text, uses «المراقبة». Friendly and
marketing copy may say «المتابعة» and «الحماية». Never «التجسس». Text a child reads is short and kind,
and tells them what they can do next («اطلب السماح»). No competitor is named: «تطبيقات الرقابة
الأبوية الرائدة» (maintainer, 2026-11-12).
