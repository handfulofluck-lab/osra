# Localization (English and Arabic)

The parent app ships English and Arabic UI. Arabic is a right-to-left (RTL) language, so a
translation is not finished until the same screen also lays out correctly in RTL.

## Layout

| Path | What it is |
|---|---|
| `apps/parent-app/l10n.yaml` | Generation config: ARB directory, English template, output class `AppLocalizations` |
| `apps/parent-app/lib/l10n/app_en.arb` | English template — the source of truth for keys and placeholders |
| `apps/parent-app/lib/l10n/app_ar.arb` | Arabic translations, one entry per English key |
| `apps/parent-app/lib/l10n/app_localizations*.dart` | Generated by `flutter gen-l10n`; do not edit by hand |
| `apps/parent-app/lib/l10n/l10n.dart` | `context.l10n`, `context.localeName`, and label maps for API values (categories, severities, command states) |
| `apps/parent-app/lib/providers/locale_provider.dart` | Persisted override (`app_locale`: `system` / `en` / `ar`) |

`MaterialApp` in `lib/app.dart` receives `localizationsDelegates` and `supportedLocales` from
`AppLocalizations`, and `locale` from `localeProvider`. A `null` locale follows the device;
Settings → Appearance can pin English or Arabic. The choice is written to
`shared_preferences` under `app_locale`, the same way `theme_mode` is persisted.

## Add a string

1. Add the key and English copy to `lib/l10n/app_en.arb`. Give every placeholder a type:

   ```json
   "screenTimeValue": "{minutes} / {limit} min",
   "@screenTimeValue": {
     "placeholders": {
       "minutes": { "type": "int" },
       "limit": { "type": "String" }
     }
   }
   ```

2. Add the same key to `lib/l10n/app_ar.arb` with real Arabic (not a transliteration), and use
   ICU plural categories where Arabic differs — `zero`, `one`, `two`, `few`, `many`, `other`:

   ```json
   "callsCount": "{count, plural, =0{لا مكالمات} =1{مكالمة واحدة} =2{مكالمتان} few{{count} مكالمات} many{{count} مكالمة} other{{count} مكالمة}}"
   ```

3. Run `flutter gen-l10n` (or `flutter pub get`). The generated files are checked in.
4. Use `context.l10n.yourKey` in the widget. For dates use
   `DateFormat.yMMMd(context.localeName)`, not the process default.
5. Run `flutter test test/localization_test.dart`. It fails if the Arabic key is missing,
   empty, has different placeholders, if a category in the server's `InternalAlertSchema` has no
   title in either locale, or if any translated screen overflows at 320×568 in RTL.

Do not add a user-visible literal to a screen. Values that arrive from the API (app names, child
names) stay as the server sent them; enum-like values (web-filter categories, alert categories and
titles, search risk tags, command types, severities) are mapped through `l10n.dart` so the raw value
is never shown when a translation exists. The one deliberate exception is an alert category the app
does not know yet: English shows the server's own title, any other locale shows the translated
generic, so server English never reaches an Arabic screen.

## Add a language

1. Copy `app_en.arb` to `app_<code>.arb`, set `@@locale`, and translate every value. Keep the
   key set identical; `flutter test test/localization_test.dart` enforces that for Arabic today
   (add the new file to that test's parity check when a third language lands).
2. Add the language to `supportedLocales` automatically — it is generated from the ARB files.
3. Add the display name and a provider choice:
   - `lib/providers/locale_provider.dart`: map the code in `appLocaleFromName`.
   - `lib/features/settings/appearance_screen.dart`: add a dropdown item and its two status
     strings.
4. Add one Arabic-style widget test per screen for the new language: locale, explicit
   `Directionality`, 320×568, no overflow.
5. If the language is RTL, it needs no code change beyond step 1 — the layout rules below are
   direction-agnostic.

## Android child agent

The child agent does not use ARB. Its strings are Android resources: `res/values/strings.xml` is
English and `res/values-ar/strings.xml` carries Arabic (today the ADR-0031 reset-code notice; keys not
translated there fall back to English). That notice is centred, so it reads correctly in RTL without a
manifest-wide `android:supportsRtl` change — with one exception that must stay: **the reset code is
set `TextDirection.Ltr`**, because `1234 5678` has no strong character and an RTL paragraph would
render it `5678 1234`. Add new user-visible copy to both files. **Counted copy is a `<plurals>`
resource in both files, read with `pluralStringResource`**: Arabic needs all six CLDR quantities
(`one`, `two`, `few` for 3–10, `many`, `other`, `zero`), so a plain `%1$d دقيقة` is ungrammatical for
most of a code's life. `ResetCodeStringsTest` compares the EN and AR key sets across strings and
plurals alike.

## RTL rules for screens

- Use `EdgeInsetsDirectional` / `AlignmentDirectional` and `start`/`end`; never
  `EdgeInsets.only(left:)`, `EdgeInsets.fromLTRB`, or `Alignment.centerLeft` for chrome.
- Do not hard-code `TextDirection`. `MaterialApp` derives it from the locale; tests wrap a
  screen in `Directionality(textDirection: TextDirection.rtl)` to prove it.
- `Row`, `Wrap`, `TabBar` and `AppBar` actions mirror automatically. Prefer `Wrap` over a
  fixed `Row` where translated labels are longer, and make tab bars scrollable when four or
  more labels must fit 320 px.
- Directional icons (`Icons.chevron_left/right`, `arrow_*`) mirror from their
  `matchTextDirection` flag; check any icon that does not.
- `apps/parent-app/android/app/src/main/AndroidManifest.xml` sets `android:supportsRtl="true"`
  for native widgets and the app-switcher label.

## What is translated

English and Arabic are complete for: the first-run wizard (welcome, sign in / create account,
add your child, pair their device, done), login, dashboard, child detail (including the command
labels and the embedded social tab), alerts and the alert detail dialog, the rules editor (all four
tabs and dialogs), reports, usage history, the pairing QR screen, and Settings → Appearance. The
snippet-vault modal is translated too. The conversation-coach card is bilingual by design (EN/AR)
and defaults to the app locale.

The four screens that used to be listed as missing are **done**, each with Arabic RTL rows at
320×568: search & web safety (#275), digest preferences (#277), the family members screen
(**#420**, `e60ad33`, 23 keys — roles and invite permissions render through
`mfaResetRoleName` / `familyPermissionName` instead of the raw wire value), and the family map
(**#424**, `bbd9745`, 18 keys — including the marker sheet's date, which now formats with
`context.localeName`). The parent alert push wording is localised on both platforms in **#421**
(`71f20a1`).

## What is not translated yet

- The verifiable parental consent notice (`consentNotice`) is intentionally left in English:
  legal wording needs a product/legal decision. It is the other open half of roadmap 3.1; the issue
  that used to track it (**#159**) was closed on 2026-10-23 for the screen review, so this line is
  currently its only written record.
- Alert bodies, and the title of a category the app does not know yet in English, are displayed as
  the server sent them; titles for the server's 13 categories come from the mapping in `l10n.dart`.
  AI coach content is displayed as supplied; the coach content itself already has an Arabic version
  authored separately.

Native-speaker review of the Arabic screenshots is the acceptance for roadmap item 3.1. Karim
reviewed the first **14 screens** and that pass is closed (#159, 2026-10-23); the strings added since
— 41 of them, on the family members and family map screens — are tracked in **#426**, together with
the wording questions the implementation flagged.
